# Lore Vault — 設計簡報（Design Brief）

> 給 UI/UX 設計 agent 的專案入門文件。假設你對本專案一無所知，讀完這份即可開始設計。

## 一、這是什麼

**Lore Vault 是一個「給 AI agent 與使用者共用的個人知識庫」的管理介面。**

使用者（開發者本人）平常讓多個 AI coding agent（Claude Code、Codex）在不同專案工作。
agent 會把決策、踩坑、交接寫成筆記存進 Lore Vault，之後再查回來；另外還有一套自動記憶層，
從對話中蒸餾出「模型容易犯錯的地方」，在 agent 編輯檔案時自動提醒。
除了專案開發，Lore Vault 也承載使用者的**世界觀構築**與**私人筆記**，並能存放文件（設定檔、簡報、PDF），
未來會讓另一個 AI 系統（U.E.P）讀取世界觀資料。

agent 透過 MCP 工具存取；**人類則透過你要設計的這個介面瀏覽、搜尋、編輯與維護**。

**重要背景**：單一使用者的個人基礎設施，不是大眾產品。設計可以大膽、個人化，
不需要 onboarding、多租戶或商業化情境。資料量級：數千則筆記、數十份文件。

## 二、核心概念與詞彙

| 詞彙 | 意義 |
|------|------|
| **Space（領域）** | 最上層分群：`dev`（專案開發）、`lore`（世界觀）、`personal`（私人）。一次只看一個 space，切換是明確動作 |
| **Vault（庫）** | space 底下的一個範圍，通常對應一個專案 repo（如 `github.com/org/repo`），也可以是一個主題。有顯示名稱與別名（專案改名時舊名字仍能對應） |
| **Note（筆記）** | Markdown 文字：標題、摘要、正文、標籤（topics）、`[[標題]]` 互連、更正關係（新筆記取代舊筆記） |
| **摘要（Summary）** | 1–2 句，由 LLM 在背景自動產生。尚未產生時暫以正文首段頂替，**介面須標明來源**（摘要／首段） |
| **Document（文件）** | 上傳的檔案（md/txt/pdf/docx/pptx/json/yaml/toml 等），背景抽出文字切成段落供搜尋；有抽取狀態（處理中／完成／失敗＋原因）與版本 |
| **Recall（檢索）** | 搜尋：全文＋語意混合，結果只列標題與摘要，點開才看全文；結果可能是筆記或文件段落 |
| **降級（Degraded）** | 語意檢索暫時不可用（例如本機模型沒開）時，只用關鍵字搜尋——**結果必須標示為降級**，不能看起來像正常結果 |
| **Concept（記憶概念）** | 自動記憶層蒸餾出的一句陳述（例如「這個 repo 已有某元件，不要重寫」），有範圍（哪個 repo／通用）、錨點（檔案、符號）、校準分數 |
| **Episode（對話輪次）** | 自動收集的 agent 對話紀錄，依機器、專案歸屬，是記憶層的原料 |
| **Doctor（健檢）** | 全系統對帳報告：每項 pass／warn／fail／skipped，附說明與計數 |
| **墓碑（Tombstone）** | 被刪除的筆記留下紀錄，避免重新匯入時復活；可以復原 |

## 三、需要設計的畫面

平台：**網頁**，桌面優先，手機可用（假設，實際技術選型由工程端定）。對外經 `pm` 子網域存取。
需含深色模式（使用者主要用深色）。

1. **連線設定**：服務位址與存取金鑰（token）、連線測試。技術性畫面，簡潔即可
2. **Space 切換與 Vault 列表**：
   - 目前 space 要時時可見；切換 space 是明確動作
   - vault 列表：顯示名稱、key、筆記數、文件數、最近更新、來源（手動建立／收料自動建立／管線建立）
   - 建立 vault、編輯顯示名稱
3. **搜尋（核心畫面）**：
   - 搜尋框（中英混合、關鍵詞堆疊是常態）、vault 篩選（單一或本 space 全部）
   - 結果清單：標題、摘要（標明是摘要或首段頂替）、所屬 vault、類型（筆記／文件段落＋頁碼或投影片號）、更新時間
   - **降級狀態、結果被字數預算截斷**都要可見
4. **筆記檢視與編輯**：
   - Markdown 閱讀（技術文本多：程式碼區塊、表格、中英混排）
   - `[[標題]]` 連結可點；更正鏈（此筆記取代了誰、被誰取代）
   - 編輯時若別人（通常是 agent）已先改過 → **版本衝突**畫面：顯示目前版本，讓使用者決定
   - 新增筆記時，系統會回報「疑似重複」清單，讓使用者決定改寫既有筆記或照樣新增
5. **筆記列表**：依 vault 分頁瀏覽、依標籤與時間篩選
6. **文件**：
   - 上傳（拖放）、列表（檔名、類型、大小、抽取狀態、版本）
   - 文件檢視：抽出的文字依頁／投影片／段落呈現，可從搜尋結果直接跳到對應位置
   - 抽取失敗要顯示原因（加密、損毀、無文字層等）並可重試
   - 上傳新版本（舊版保留、標示被取代）
7. **Vault 維護**：
   - **別名管理／重新導向**：專案 repo 改名時，把新 key 導向既有 vault（使用者明確要求預留）
   - 同名 repo 以組織名區分（`org/repo`）
   - 把 vault 移到另一個 space
   - 刪除筆記或整個 vault（二次確認），墓碑檢視與復原
8. **系統健康**：
   - Doctor 報告：分類列出每項檢查的狀態、說明、計數；fail／warn 要醒目
   - 背景補算進度（待補摘要／向量筆數、失敗數，失敗可重試）
   - 最近一次備份時間、語意模型暖機狀態、各機器的收料新鮮度
9. **記憶層（唯讀為主）**：
   - Concept 瀏覽：陳述、範圍、錨點、校準結果；依 repo／通用篩選
   - 收料概況：各機器、各專案的 episode 數與最近時間（不需顯示對話原文）

## 四、設計上值得思考的點

- **Space 的氛圍區隔**：`dev` 是工程工具感；`lore` 是世界觀創作；`personal` 是私人空間。
  使用者要一眼知道自己在哪個 space，避免把私人內容誤存到開發區（open question，歡迎提案）
- **狀態的誠實呈現**：降級、截斷、摘要尚未產生、抽取失敗、補算積壓——這是工具，不能假裝一切正常。
  本專案的頭號原則是「不讓錯誤靜默發生」
- **資訊密度**：搜尋結果只給標題與摘要是刻意的（先索引、後全文）；全文閱讀要舒適
- **agent 與人共寫**：很多筆記是 agent 寫的，人類主要是審閱、修正、整理；版本衝突與重複偵測是日常
- **CJK 排版**：大量中英混排與程式碼，等寬字型與中文字型的搭配品質很重要
- **桌面 vs 行動**：桌面可三欄（vault 列表｜結果或列表｜內容），手機收合導航

## 五、限制與非目標

- 不需要設計：登入／註冊（單使用者、token 即可）、多人協作、權限角色、
  對話式問答（chat／ask）、Podcast、模型與供應商管理
- 使用者介面語言：**繁體中文**
- 品牌／風格沒有既定包袱，專案名「Lore Vault」
- 設計不受現有 API 約束，但工程端需要補的端點（別名管理、刪除、文件、concept 瀏覽等）會依設計排入
